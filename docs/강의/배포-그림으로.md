# 배포, 그림으로 — 코드 먼저, 데이터 이사는 나중

## 1. 한 장 요약

코드 세 벌(엔진 → ERP → 고객 화면)을 먼저 내보내고 그다음 prod 서버에서 손으로 데이터 이사(마이그레이션 0013)를 돌린다. 파이프라인은 migrate 를 돌리지 않는다. 워크플로·스크립트·Dockerfile 어디에도 그 단어가 없다.

## 2. 왜 그 순서인가

| | 옛 데이터 (`2`) | 새 데이터 (`A2`) |
|---|---|---|
| 옛 코드 | 된다 | 안 된다 — `A2` 를 못 읽는다 |
| 새 코드 | 된다 — 숫자 키 폴백 | 된다 |

새 코드는 옛 키를 읽는 폴백이 있다. 옛 코드는 새 키를 못 읽는다. 그래서 코드가 다 나간 뒤에 데이터를 옮기면 깨지는 창이 없다.

## 3. DB 에서 바뀌는 것

표(테이블)는 둘만 건드리고 스키마는 그대로다. ALTER 는 한 줄도 없다.

| 테이블 | 무엇을 | 로컬 실측 |
|---|---|---|
| `stay_productprice` | `occupancy_key` 값만 바꾼다. `"2"` → `"A2"` | 95,829행 |
| `stay_productprice` | 같은 자리에 `A<n>` 이 이미 있는 숫자 셀을 지운다 | 84행 |
| `stay_productpricevalue` | 지운 셀에 딸린 값 행을 함께 지운다 | 84행 몫 |
| `django_migrations` | `('stay', '0013_normalize_occupancy_keys')` 한 줄이 들어간다 | 1행 |

로컬 DB 에서 실제 SQL 을 잡아 봤다(트랜잭션 안에서 돌리고 롤백). UPDATE 53문, DELETE 2문, SELECT 4문. 행 하나씩 가지 않고 id 묶음으로 간다.

```
UPDATE `stay_productprice` SET `occupancy_key` = 'A2' WHERE `stay_productprice`.`id` IN (196132, 195916, …)
DELETE FROM `stay_productpricevalue` WHERE `stay_productpricevalue`.`product_price_id` IN (337063, 337105, …)
DELETE FROM `stay_productprice` WHERE `stay_productprice`.`id` IN (337063, 337105, …)
```

보류 61건은 로컬 오퍼 188 이야기다. 유료 연령 구간이 둘(ADULT · CHILD)이라 코드 없는 `A2C1` 이 어느 구간의 1명인지 정해지지 않아 그대로 둔다. prod 에 이런 오퍼가 있으면 dry-run 이 목록을 내고, 사람이 정한다.

## 4. django_migrations 에도 남나

`migrate stay` 로 돌리면 남는다. `showmigrations stay` 에 `[X] 0013` 으로 찍히고 다시는 안 돈다. `sqlmigrate stay 0013` 은 "THIS OPERATION CANNOT BE WRITTEN AS SQL" 만 낸다. RunPython 마이그레이션이라 SQL 이 미리 정해져 있지 않아서다. 위 SQL 은 실제로 돌려 잡았다.

관리 커맨드 `stay_normalize_occupancy_keys` 로 돌리면 데이터는 같게 바뀌지만 `django_migrations` 에는 안 남는다. 나중에 migrate 가 0013 을 또 돌리는데 같은 규칙이라 0건 처리로 끝난다. 그래도 prod 는 migrate 로 돌린다. 기록이 남아야 한다.

## 5. Stay 밖에는 영향이 없다

| 저장소 | 바뀐 파일 | Stay 밖 |
|---|---|---|
| ERP (basecamp) | 68 | 2 — `common/templates/common/_htmx_stay.html` · `fit/views/reservation.py` |
| 엔진 (homepage-backend) | 20 | 0 — 전부 `stay/` 패키지 |
| 고객 화면 (website-ui) | 27 | 0 — 전부 `src/stay/` 와 `__tests__/stay/` |

ERP 의 두 파일 중 하나는 Stay 전용 htmx 로더고 include 하는 곳이 Stay 템플릿 넷(`master_list` · `master_editor` · `staff_reservation_create` · `cancellation_policy_list`)뿐이다. 레거시 화면 셋은 옆의 `_htmx.html` 을 그대로 쓴다. 다른 하나는 `fit/views/reservation.py` 한 곳이다. 추가수집정보 탭을 저장할 때 `optional_info` 를 통째로 바꾸는 대입이 있었다. 이제 Stay 의 병합 헬퍼를 호출한다. 다른 키는 그대로 두고 `stayOccupancy` 만 지킨다. 공용 모델·URL·시그널·설정 변경은 0, 정적 파일(S3) 변경도 0 이다. 마이그레이션이 `fit` 을 읽기는 한다(`masteroption.offer_id`, 읽기만). 그래서 `fit.0165` 뒤에 서게 해 뒀고 prod 에는 이미 있다.

## 6. 코드 리뷰 결과

리뷰어 여섯이 세 브랜치를 봤다. Claude(opus) 셋은 커밋 범위, Codex(gpt-6-astra, reasoning high) 셋은 `origin/develop...HEAD` 범위. 원문은 리뷰 전문 페이지에 있다: https://claude.ai/code/artifact/61ebcc4f-da35-46fd-9941-e4bdf484c812

| 리뷰어 | 대상 | 판정 | 발견 |
|---|---|---|---|
| Claude | ERP | 조건부 | 높음 4 · 중간 2 · 낮음 2 |
| Claude | 엔진 | 조건부 | 심각 2 · 보통 3 · 낮음 4 |

여섯 판정을 합치면 "고치기 전에는 내보내지 말 것"이다. 그래서 고쳤다. 아래는 고친 것과 남긴 것이다.

**고친 것 — ERP** (테스트 2218 → 2268)

- 마이그레이션 0013 을 한 트랜잭션으로 감쌌다. MySQL 은 RunPython 을 자동으로 감싸지 않아 2,000행 묶음마다 따로 커밋됐는데 이제 전부 아니면 전무로 끝난다.
- 재실행이 멱등이다. `"2"` 와 `"02"` 처럼 1회차가 보류한 셀을 2회차가 지우던 것을 막았다. 선행 0 키는 언제나 보류다.
- 비활성(`use_flag=False`) `A2` 는 활성 숫자 셀을 못 지운다. 생존 후보는 활성 행만이고, 아니면 보류다.
- 코드 없는 `A2C1` 과 `A02C1` 이 같은 `A2C1_CHD` 로 가려다 UNIQUE 에 걸리던 것을 보류로 돌렸다.
- 옛 규칙 연령 구간 코드(`CHILD_UNDER12`)가 견적을 500 으로 만들던 것을 성인 취급 + 경고로 바꿨다.
- 코드 없는 `A2C1` 후보는 그 오퍼의 유료 구간이 정확히 하나일 때만 넣는다. 문서와 마이그레이션이 이미 그 규칙이었다.
- 유료 아동인데 조합 셀이 없으면 성인 전용 `A2` 로 내려가 아이 요금이 사라졌다. 이제 머릿수 `A3` 로 간다. 옛 총원 규칙과 같은 값이다. 조합 셀도 `A3` 도 없는 계약은 과소 청구 대신 판매 불가로 접힌다. 이 선택은 James 확인이 필요하다.
- 다객실·성인만 요청의 폴백에서도 A-형이 숫자보다 먼저다.
- 직원 예약이 실패한 화면에서 견적을 재조회할 때 여행사·마스터 조건을 걸었다. 다른 여행사 견적의 아동 정보가 그 화면에 나오지 않는다.
- `los_prices`·`occupancy_adjust` 의 dict 입력도 문자열과 같은 검증을 지난다. 파서는 `A2C1_C1_CHD` 같은 혼합 형식과 33자 결과를 거부한다.
- 삭제 예정 셀을 CSV 로 떠 두는 `--dump-deletes` 옵션을 더했다. 확인창은 마스크를 눌렀을 때만 닫힌다.
- 맨 숫자 셀을 지우기 전에 살아남는 A-형 셀과 가격·정가·상태·권위값을 대조한다. 하나라도 다르면 지우지 않고 보류로 남긴다. 활성 A-형이 둘 이상이어도 보류다.
- FIT 예약 상세의 추가수집정보 탭을 저장해도 `stayOccupancy` 가 남는다. James 가 배포 차단으로 지정해 `fit/` 한 곳을 고쳤다.

**고친 것 — 엔진** (Stay 테스트 696 → 710, DB 미접속 9건은 전과 같음)

- ERP 와 같은 네 규칙: 코드 없는 후보 가드, 머릿수 폴백, 폴백의 A-형 우선, 읽지 못한 구간 코드는 성인 취급 + `AGE_BAND_CODE_UNREADABLE` 경고.
- 견적 요청에 optional `children` 을 받아 룸 리스트와 같은 "나이가 다 왔나" 판정을 한다. 나이 없는 옛 요청에서 목록 130 · 견적 150 으로 갈리던 답이 같아진다.
- 최종 필터가 정규화 키로 비교한다. `a2` 와 `A2` 가 한 좌표다.
- 잘못된 키마다 예외를 만들던 자리를 `parseKeyOrNull` 로 바꾸고 LOS 주석과 원장 문구를 새 규칙으로 고쳤다. 조합 좌표를 못 만든 요청에 `OCCUPANCY_WITHOUT_PARTY` 경고를 남긴다.

**고친 것 — 고객 화면** (Stay 테스트 974 → 995)

- 키 파서를 순차 파싱으로 다시 썼다. 5초 넘게 돌던 123자 악성 키가 1ms 안에 거부되고 `A2_C1_CHDC1_TEEN` 처럼 반만 읽히던 키를 거부한다.
- 재조회 중에는 이전 가격 옆에 새 아이 나이가 붙지 않는다. 화면에 있는 행을 만든 검색 인원을 함께 들고 다닌다.
- 검색 인원 주석을 본문 캡션으로 내렸다. 터치·키보드에서도 보인다.
- 마이페이지 성인 행의 나이 표기, 아이 수 불일치 주석, `CHILD_AGE_MAX` 단일 원천, React key 중복을 고쳤다.
- 견적 요청에 `children` 을 싣는다. 결제 준비 요청의 `selection` 에서는 뺀다. ERP 가 selection 전체를 해시하므로 실으면 모든 예약이 튕긴다.

**남긴 것** — 8절에 적었다. 박수 층을 날짜별로 고르기, 요청 박수 이하 층이 없을 때 최소 층으로 내려가는 폴백. 리뷰가 짚은 데이터 점검 둘(옛 규칙 구간 코드, 박수 층 둘 이상인 좌표)은 7절 체크리스트에 들어갔다.

## 7. 순서대로 할 것

1. 엔진: `feat/stay-age-band-cells-engine` PR #956(develop 머지 완료) → stage 푸시(자동) → prod 수동 dispatch.
2. ERP: `feat/stay-age-band-cells` PR #9096(develop 머지 완료) → stage 푸시 → prod 수동 dispatch(service=erp).
3. 고객 화면: `feat/stay-child-age-label` PR #2456(develop 머지 완료) → stage → prod.
4. 배포 직후 확인: 시즌 [가격] 드로어에 `아동 추가 금액` 칸, 씨센스 43886 고객 페이지 금액 그대로.
5. prod 서버: `python manage.py showmigrations stay | tail -3` → `[X] 0012` · `[ ] 0013`.
6. prod 서버: `python manage.py stay_normalize_occupancy_keys --dry-run --dump-deletes /tmp/0013_deletes.csv` → 변경·삭제·보류 건수. 보류가 있으면 목록을 보낸다. 삭제 예정 셀은 CSV 로 남는다.
6-1. prod 서버: `python manage.py migrate stay --plan` → 걸리는 것이 0013 하나뿐인지 본다. fit 이 같이 걸리면 멈춘다.
6-2. prod DB 에서 옛 규칙 연령 구간 코드 점검. 0건이어야 한다.
   ```
   SELECT offer_id, code FROM stay_offerageband WHERE code NOT REGEXP '^[A-Z0-9]{2,8}$';
   ```
7. prod DB 에서 박수 층 점검 한 번. 엔진 리뷰가 짚은 항목이다. 층이 둘 이상인 좌표가 0이면 새 박수 규칙은 답을 바꾸지 않는다. 있으면 그 계약의 큰 층이 "박수 이상이면 이 1박 단가"인지 확인한다.
   ```
   SELECT product_id, rate_plan_id, occupancy_key, COUNT(DISTINCT los_nights) AS layers
   FROM stay_productprice GROUP BY 1,2,3 HAVING layers > 1;
   ```
8. DB 스냅샷. 되돌리기는 복원뿐이다. 이사하는 동안 ERP 에서 가격을 고치지 않는다(점검 창, 몇 분). 이사는 한 트랜잭션이라 짧다.
9. prod 서버: `python manage.py migrate stay` → 처리 건수 확인.
10. prod 서버: dry-run 다시 → 0건.
11. 씨센스 43886 고객 페이지 · 직원 예약 화면 · 편집 화면 가격 캘린더(옛 형식 배지 0) 확인.

## 8. 남긴 것 (후속, 배포를 막지 않음)

- 박수 층을 체류 전체에서 하나로 고른다. 어떤 날에만 층이 더 있으면 그 날만 남고 나머지 날이 빈다. 시즌 채우기는 층을 시즌 전체에 고르게 깔아 평소엔 안 생기지만, 날짜별 선택으로 바꾸는 것이 다음 순번이다(ERP·엔진 같이).
- 요청 박수 이하 층이 하나도 없으면(2박인데 `3박~` 층뿐) 가장 작은 층으로 물러난다. 방이 이유 없이 사라지지 않게 한 설계이고 ERP·엔진이 같다. 엄격하게 바꿀지는 James 결정.
