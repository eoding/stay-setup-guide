# 호텔·룸 팩트 수집 가이드

지시서(manual.md)를 쓰려면 계약서(가격표)만으로는 부족하다. 호텔 소개문, 시설 목록, 룸의 면적·전망·침대
구성 같은 "팩트"가 따로 필요하다. 이 문서는 그 팩트를 어디서, 어떤 순서로 찾아 `facts.json` 에 담는지 정리한다.
예시는 `examples/우에노_토우가네야/facts.json` 을 본다.

## 1. 필요한 필드 목록

**호텔**
- 한글 상품명 / 영문명
- 주소(도로명 전체), 전화, 이메일
- 체크인 / 체크아웃 시각
- 성급(star)
- 개장 연도 / 리노베이션 연도(있으면)
- 총 객실 수
- 위도 · 경도(소수 6자리)
- 시설·서비스 목록
- 소개문(한 줄 + 상세)

**룸(타입별)**
- 면적(㎡)
- 전망(오션뷰/가든뷰/마운틴뷰 등)
- 침대 종류 + 개수(여러 구성이면 구성별로)
- 기준 인원(성인) / 최대 인원(성인·소아·총원)
- 어메니티 목록
- 층(있으면)

## 2. 출처 우선순위

1. **여행사가 이미 팔고 있는 판매 페이지**(있으면) — 한글 상품명·소개문·룸 표시명의 정본. 실제 고객에게 보이는
   문구이므로 다른 출처보다 우선한다.
2. **호텔 공식 사이트** — 룸별 개별 페이지가 있으면 면적·전망·침대·어메니티가 가장 정확하다.
3. **여행 예약 사이트 상세 페이지** — 면적·침대·인원 수·룸 어메니티·호텔 시설·체크인/아웃·개장연도가 페이지에 정리돼 있는 경우가 많다. 공식 사이트에 없는 어메니티·시설 목록은 여기서 채운다. 사진은 여기서 가져오지 않는다(공식 사이트 것만).
4. **호텔이 보내 준 자료**(팩트시트·소개 자료·계약서 부록).

위 어디에도 없는 값은 지어내지 말고 `비움` 으로 두고 `changes.md` 의 `## 담당자가 채울 칸` 에 적는다.

같은 항목을 여러 출처가 다르게 말하면, **확인된 값**(가장 근거가 뚜렷한 값)을 채택하고 추정이 아닌 값으로
적는다. 상세설명 문장도 채택한 값에 맞춘다. 확실하지 않은 값은 `facts.json` 의 `_estimated` 목록에 이유와
함께 남긴다.

## 3. 좌표 찾기 순서

위도·경도는 다음 순서로 찾고, 못 찾으면 비워 두고 담당자가 나중에 채운다.
1. 판매 페이지에 지도가 있으면 그 좌표.
2. 여행 예약 사이트 상세 페이지에 적힌 좌표 숫자.
3. OpenStreetMap(Nominatim) 에서 정확한 상호로 검색해 나온 좌표. 같은 이름의 다른 지점에 주의.
4. 셋 다 없으면 `비움` 으로 두고 `changes.md` 의 `## 담당자가 채울 칸` 에 적는다.

좌표는 **소수 6자리**로 고정한다(`16.068000`). 7자리 이상은 화면이 저장을 거부한다.
**같은 브랜드의 다른 지점**(예: 같은 체인의 다른 도시 지점)과 혼동하지 않도록 상호·주소를 같이 대조한다.

## 4. facts.json 스키마

`examples/우에노_토우가네야/facts.json` 과 같은 구조를 쓴다. 핵심 필드:
- `hotel`: name_ko, name_en, address, phone, email, checkin, checkout, star, opened_year,
  renovated_year, total_rooms, lat, lng, description_ko, facilities(배열)
- `rooms`: card_name(지시서의 룸 이름), name_ko, area_m2, view, bed, max_adults, max_children,
  max_guests, floor, amenities(배열), description_ko, source_url
- `_estimated`: 확정하지 못하고 추정으로 채운 필드와 그 이유를 적는 목록
- `sources`: 값마다 출처 URL 을 빠짐없이 적는다(주소·전화·면적·침대·좌표·시설 등 필드별). 지시서 본문에는 옮기지 않지만 담당자가 값을 확인할 때 이 목록을 본다.

## 5. 사진

**사진 저작권은 사용자 책임입니다.** 이 스킬이 찾거나 내려받는 사진(호텔 공식 사이트 등)의 저작권·사용 허락 확인은 전적으로 사용자(여행사)의 책임이며, 이 스킬의 제공자는 사진의 권리 문제에 대해 어떠한 책임도 지지 않습니다. 판매 화면에 올리기 전에 호텔로부터 사용 허락을 받으십시오. `사진목록.txt` 첫 줄에도 이 문장을 넣고, 파일마다 출처 URL 을 적어 사용자가 확인할 수 있게 한다.

파일명 규칙(공유 폴더의 `사진/` 안에 그대로 저장):
- `hotel_01.jpg` ~ `hotel_08.jpg` — 호텔 전경·시설 사진(최대 8장)
- `room_<룸 slug>_01.jpg`, `room_<룸 slug>_02.jpg` — 룸별 사진(룸마다 2장)
- `offer_hero.jpg` — 오퍼 대표 이미지 1장

용량·크기 기준: 사진 한 장은 10MB 이하, `offer_hero.jpg` 는 5MB 이하. 가로 1200px 이상을 권장한다.
어느 사진을 어디서 받았는지는 `사진목록.txt`(또는 각 사진 폴더의 목록 문서)에 파일명·출처를 같이 적어 둔다.

## 도시 코드

ERP 의 `도시` 칸은 공항코드(IATA 3자)로 검색해 고르는 자동완성이고, 항목 글자는 `한글명(공항코드)` 다(예 `다낭(DAD)`, `푸꼭(PQC)`, `냐짱(나트랑)(CXR)`, `도쿄(TYO)`). 화면의 한글 표기는 담당자가 부르는 이름과 다를 수 있으므로(푸꾸옥→푸꼭, 나트랑→냐짱) **코드를 먼저 확정하고 화면 항목 글자를 그대로 옮긴다.**

1. 코드 찾기: 호텔 공식 사이트 오시는 길(가장 가까운 공항) → 예약 사이트의 공항 거리 표기 → 항공권 사이트의 도시 코드. 도시에 코드가 여럿이면 도시 대표 코드(도쿄 TYO, 서울 SEL)를 쓰고 개별 공항 코드(HND·NRT)는 쓰지 않는다.
2. 화면 항목 확정: 지시서의 `도시 확인` 단계가 그 코드를 쳐서 뜨는 항목 글자를 확인하는 자리다. 코드가 화면에 없으면 `changes.md` 에 적고 사용자에게 묻는다.
3. `facts.json` 에 `hotel.city_code` 로 적고, 지시서 `도시` 값은 `선택: <화면 항목 글자 그대로>` 로 쓴다.
